## v0.6.3 — scrolling capture on a real Mac (Mac mini M4, macOS 26.5.2)
- Reported (user's screenshot of the result): the image contained Lumora's own scroll control ("请缓慢滚动… · 已截取 1 帧 · 取消 · 完成") at the bottom of the area; the frame count stayed at 1 while scrolling a chat web app (sticky input bar, scrolling message list).
- Root causes: (1) self-exclusion used the window list of a snapshot fetched right after the control was shown, so the control could be missing from it (not yet on screen / created after) → captured; (2) the control's fallback position (`visible.min_y()+24`) put it inside a full-height area; (3) the stitcher's exact full-width row hashes + downward-only growth: reproduced against the v0.6.2 code on synthetic chat pages — scrolling up → every frame `ScrolledUp` (count 1); a fixed sidebar, the overlay scrollbar, ±2 px-value noise, or our translucent control inside the area → every frame `Restarted` (count 1). Which of these hit the user is not yet known (needs the new log).
- Fixed: `SCContentFilter(display:excludingApplications:exceptingWindows:)` with our `SCRunningApplication` (window-list fallback), content fetched incl. off-screen windows and refetched once the control is up; control placed below / above / beside / screen corner, ignores the mouse if forced inside; stitcher with 64 cell means per row (tolerance 6/255, 6 % mismatch), fixed top/bottom bands, fixed-column masking, upward growth (`Push::Prepended`, `Push::Moved`), torn-frame checks; per-frame debug log and info summary.
- Unverified on hardware: Lumora listed in `SCShareableContent.applications` (else the warn + fallback path); stitching on Safari / Chrome / Electron chat apps with momentum scrolling; colour-managed or HDR displays; frames per second / CPU at 2× on large areas (~17 ms per 2880×1800 frame in a Linux release benchmark).

## v0.6.2 — real-Mac fixes (Mac mini M4, macOS 26.5.2)
- Confirmed (from the user's recording, cursor y + ripple y ≈ constant): click ripples were mirrored vertically. Root cause: `layer_host_view` hosted a `geometryFlipped` root layer in a plain bottom-up `NSView`; AppKit keeps a hosted root layer's flip in step with the view's `isFlipped`, so the y-down drawing came out mirrored. Fixed with a flipped `LumoraLayerHostView` (also `KeyCatcherView`); callers audited (click overlay, keystroke HUD, recording border, shutter, countdown). Pure helper `geometry::appkit_to_local_top_down` with multi-screen tests.
- Reported: scrolling capture saved immediately after one click. Root cause (reproduced in core tests against the v0.6.1 stitcher): the focusing click changes the window in place on every row (> 4 % tolerance), no shift lines up → `Push::NoOverlap` on frame 2 → session finished and saved one frame. Fixed: in-place changes ≤ 25 % of rows = unchanged; before the first scroll a non-matching frame restarts the stitch; after it, 12 lost frames in a row (~2 s) before stopping; frame errors retried (3); no automatic end before a scroll; Done ignored for 0.35 s and ↩ auto-repeat ignored; every end logged at info.
- Unverified on hardware: ripple / keystroke HUD / countdown / shutter orientation after the flipped-view change; scrolling capture after a focusing click on real apps (Safari, Finder, Xcode), smooth-scroll fractional offsets, animated pages.

## v0.6.1 — first real-Mac findings (Mac mini M4, macOS 26)
- Confirmed root cause of "capture does nothing": the onboarding window, once closed with its close button / Esc / ⌘W, stayed registered as open, so `show_onboarding` returned early and every capture + the Permission menu item did nothing. Fixed (windowWillClose → Dismiss; existing window brought to front).
- Confirmed: the onboarding window was created but hidden behind other apps (it appeared after `osascript … activate`). Fixed with deferred show, floating level, activateIgnoringOtherApps + orderFrontRegardless; visibility logged.
- Confirmed: launched from a terminal, the TCC prompt names the terminal (XTerminal) and the grant goes to it. Documented; launch warning logged.
- Confirmed: with permission granted the menu-bar icon is visible; the "app doesn't open" report was the silent menu-bar start. Fixed with a launch toast + reopen handler.
- Unverified on hardware: TCC registration via the SCK probe at launch / Grant Access, App Translocation move-to-Applications flow, login-item launch detection, hidden-status-item heuristic (occlusion), 5 s Preparing watchdog, stale-grant guidance on -3801 with preflight true, file log + panic hook.
